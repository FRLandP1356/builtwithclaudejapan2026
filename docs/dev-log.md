## 1. 詰まった場面：公式の2050年を再現したら、全国で約10%高く出た

最初のコミット（06:19、f241901）より前に、公開されている前提だけで社人研の2050年の結果を再現できるかを、使い捨ての Python の試作（リポジトリの外）で試した。時刻はリポジトリに記録が無い。試作の作業ファイルの更新日時（作者の機械の一時フォルダ。読者は確かめられない）は、05:00〜05:05ごろだった。

- 最初の計算は、全国の2050年が公式より約10%高かった。
- 年齢別に見ると、ずれていたのは0〜4歳だけで、公式の1.43倍だった。ほかの年齢は合っていた。
- 0〜4歳は「子ども女性比 × 次の期の女性の数」で出す。子ども女性比の分母を、一般的な「15〜49歳の女性」にしていたのが原因だった。社人研が公表している子ども女性比と、公表している人口から逆算して、分母は**20〜44歳の女性**と確定した。
- 直すと、前提が公表されている1,871地域で、2050年の人口のずれの中央値が0.005%になった。公表されている前提が、公式の結果の計算に使われた値そのものだった、と言える。

TypeScript のエンジン（Task 5。コミット 8da53e7、06:49）でも同じ結果を確かめた。前提が公表されている1,871地域の合計で、2025年の0〜4歳は、エンジン 3,952,306人に対して公式 3,952,307人（-0.00003%。公式の値はテストの中に、出どころを添えて固定してある）。2050年は、同じ1,871地域のずれが、中央値 0.0053%、最大 1.39%。全国の合計は、前提が公表されていない13村（公式の年齢別人口をそのまま使う）を足した1,884地域で、エンジン 104,686,401人に対して公式 104,686,386人。この再現は、テストとして常に走る（しきい値は README にある）。

### 3.4 自動のセキュリティ点検（Claude Code の機能）

作業の途中でコメントがあった。台帳に記録があるのは4回（点検の側の記録は手元にない）：(1) Worker は、画面から来た道具の定義を信用してはいけない、IP の保存は鍵つきのハッシュにする → 道具の定義を Worker の側に置き、IP は HMAC にした。(2) データ取得で、設定のファイル名から書き込み先を作っている → 設定を書くのは作者だけで悪用はできないと判断してそのままにし、修正の波で、素のファイル名だけを受け付ける検査と、ダウンロードの大きさの上限を足した。(3) 1日の回数の書き込みが失敗すると、上限が静かに外れる（中程度）→ 全体の数を16個のキーに分けた（上の3.3）。(4) 公開の日、数えられないときは止める設計にしたあと：2つのカウンターの片方だけ保存できた要求が、そのカウンターを1回分多く残す（中程度）→ 直さないと判断した。KV には取り消す仕組みが無く、同じキーへの1秒以内の2回目の書き込みは断られるため、取り消せない。影響は1回分で、断る側に倒れ、キーは2日で消える。コードのコメントと worker/README.md に書いた（6.6）。

## 4. 作業の進め方

同じ日に、作者は、AI の容量（全体で1日400回、1人60回、Cloudflare のプランはそのまま）を変えないと決めた。確認用の95回の質問の平均が2.43回の呼び出しなので、全体の400回は約165問分（400 ÷ 2.43）、1人の60回は約25問分。無料プランの KV の書き込みの枠（1日1,000回）で足りる回数は約500回で、コードの全体の上限400回より多い。プランそのものは確かめられていない。

そのあと同じ日に、作者は Cloudflare から KV の書き込みの枠についての通知メールを受け、説明を聞いて、Workers を有料（Workers Paid）に切り替えた。購入のあと、作者は、高額な請求が来ないように、上限の設定や先払いのクレジットのようなものを全て設定するよう指示した。調べた結果、Cloudflare には金額で自動的に止まる上限（ハードキャップ）が無く、予算アラートは通知だけだった（先払いのクレジットの形は、確かめた範囲では見つからなかった）。そのため、予算アラート（1・5・10・20ドル）、1回の呼び出しの上限（`limits`: CPU 100ミリ秒、外への呼び出し60回）、すぐ止める手順を設定し、`worker/README.md` の「請求の安全」に書いた。

### 6.8 3件目の保存済みの答えの作り直し

### 6.9 画面の色と最初の画面（2026-11-06）

作者は、地図の色の説明がわかりにくい（人口の変化も、支える人数も）、少ない所ほど色が薄くなるほうがわかる、大変な所ほど黒に近づけてほしい、最初の画面で何ができるアプリなのかわからない、それぞれの欄にも行けない、と指摘した。参考は、骨格を AI に任せ（Windy）、質感は SYNODOS を選んだ。

色は、人口の変化を紺 1 色の濃さだけの段（少ない所ほど薄く、2020 年と同じが `--accent`、増えた所がいちばん濃い）、支える人数を灰色から黒に近い色までの 6 段（少ないほど黒に近い）にした。段の数は、実データ（初期設定）の数え直しで決めた。2100 年の県は、8 段のとき 47 のうち 35 が同じ段に入ったので、0.4 の区切りを足して 9 段にし、4・20・15・7・1 に分けた。凡例の文言も「色は2020年の人口に対して、どれだけ残るか（薄いほど少ない）」「色は高齢者1人を支える人数（黒に近いほど少なく、大変）」に直した。

最初の画面は、題・説明・問いの下に、帯の中のメニュー「この地図でできること」を置いた。4 つの欄の名前と 1 行の説明を並べ、押すとその欄へ移動して見出しに焦点が移る（スマホでは名前の帯が画面の上に貼り付く）。見本では、色の 2 択が縦書きで読みにくかったので、横書きのままにした。地図の高さの余白は 422px から 485px にした（1280×800 から 1920×1080 まで、帯・地図・凡例・年が最初の画面に収まる）。見本の選び方は、作者が 3 案と色の見本を見て「完璧と言えるものにして」と指示したため、AI が上の帯の案を選び、弱点（縦書き、スマホで地図が下がる）を直して実装した。

## 7. 感想の材料（事実）

- 公的な統計の仕様は、公表された前提と結果を突き合わせて読み取る必要があった。ずれが出ても、年齢別に分けて見ると原因（0〜4歳の分母）が絞れた。
- 「人口の移動が止まる」前提は、全国の人口を減らす一方で、人口が減っている小さな町では増やす（田辺市の2100年は 11,880人から 13,690人）。Task 11 の報告で、画面と AI の説明に「移動が止まる＝人口が減る」と書かないよう、申し送りをした。
- 数字を出す部分（計算、AIの道具、答えの数字の検査）には、テストを先に書き、変異テストで確かめた。それでも、レビューのたびに、失敗できないテストや、入力の範囲の抜けが見つかった。
- 偽の応答に対する試験は、通っていても、本物の環境で動く証拠にはならなかった。最後の全体レビューで見つかった Worker の問題の多くは、そのためだった。
- 公開した Worker を本物のモデルで確かめると、偽の応答に対する試験では見えなかった点（長い会話で、前の質問の道具の結果にある数字が警告される、試算の最初の年の食い違い、道具では答えられない質問の例）が見つかった。一方、最後の全体レビューが公式ドキュメントと照らして直した要求の形は、235回の呼び出しで一度も 400 にならなかった。
- 日本語の公式資料（社人研の Excel、国土交通省の PDF と規約のページ）は、探せば一次資料に当たれたが、図の中の数値は文字情報が崩れていて、画像に描画して目で読み、文字情報と突き合わせる必要があった（施設の表）。
