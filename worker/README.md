# worker: Claude API の中継（Cloudflare Workers）

画面からの質問を Anthropic の Messages API に中継する小さな Worker です。API キーを画面側に置かないために使います。

## できること

- `POST /api/chat` だけを受け付けます（それ以外のパスは 404、他のメソッドは 405）。
- 本文は `{ "messages": [...] }` だけです。`messages` は、確かめた項目から作り直して送ります（余分な項目、ブロックの `cache_control`、画像や文書のブロックは届きません）。
- モデル（`claude-sonnet-5-5`）、`max_tokens`（1500）、システムプロンプト、**道具（tools）の定義**は Worker が決めます。画面から来た値は使いません。
  - 道具の定義（名前・説明・入力の形）の正本は `src/ai/toolDefs.ts` の `TOOL_DEFS` です。画面側の `src/ai/tools.ts`（道具の実装）と Worker が、この 1 つのファイルを共有します。Worker は毎回、この定義をそのまま Claude に送ります。
  - 本文に `tools`（やそのほか知らない最上位の項目）があっても、**無視します**（エラーにはしません。送られた値は一切、上流に届きません）。
  - 過去のやり取りに入る `tool_use` ブロックの道具名は、`TOOL_NAMES`（同じファイルから出る名前の一覧）にあるものだけです。ないものは 400 `invalid_messages` です。
  - 説明は 400 文字未満、入力の形（JSON にした長さ）は 2,000 文字未満に収めます（上流への要求を小さく保つため。`toolDefs.test.ts` が確かめます）。
- 本文は 64KB まで（超えると 413）。メッセージは 40 件まで、テキストの合計は 48,000 文字までです。
- 応答は上流が 200 のときだけそのまま返します。上流が 200 以外（4xx も含む）、ネットワークの失敗は、中身を見せずに 502 `{ "error": "upstream_error" }` です。
- 呼び出せる出どころは `ALLOWED_ORIGINS`（カンマ区切り、完全一致）だけです。`Origin` が無い、または違う場合は 403 です。**これは認証ではありません。** 他のウェブサイトのページの中からブラウザ経由でこの Worker を使わせない、という程度の仕組みです。`curl` などのブラウザ以外の道具は `Origin` に好きな値を付けられるので、これでは止まりません。

## 応答コード（Response codes）

エラーの応答の本文は `{ "error": "<コード>" }` です（429 だけ `"cached": true` が付きます）。コードと HTTP ステータスは `worker/index.ts` と `worker/validate.ts` のとおりです。画面側の動きは `src/ai/client.ts` の `ask()` が決めています。

| コード | HTTP | 意味 | 画面の動き |
|---|---|---|---|
| `invalid_body` | 400 | 本文が JSON のオブジェクトではない（配列や文字列など） | 汎用のエラー表示。画面は常に `{ messages }` を送るので、通常は起きません |
| `invalid_json` | 400 | 本文が JSON として読めない | 同上 |
| `invalid_messages` | 400 | `messages` が無い・空・41 件以上、テキストの合計が 48,000 文字を超える、またはブロックの形・道具名が決まりに合わない | 同上。会話が長くなると起きうるので、画面側は送る前に大きさを測って防ぎます（下の「会話の大きさの上限」） |
| `body_too_large` | 413 | 本文が 64KB（UTF-8 のバイト数）を超えた。日本語は 1 文字が 3 バイトなので、長い会話ではテキストの合計が 48,000 文字に届く前に、およそ 21,000 文字でこの上限に先に届く | 「質問が長すぎます。」。画面側は、送る前に大きさを測り、古いやり取りを自動で捨てるので、通常は届きません（下の「会話の大きさの上限」） |
| `origin_not_allowed` | 403 | `Origin` ヘッダが許可リストに無い、または付いていない | 汎用のエラー表示（保存済みの答えには切り替えません） |
| `rate_limited` | 429（`cached: true` 付き） | 1 日の回数の上限（IP ごと、または全体）に達した | 同じ質問の保存済みの答えがあればそれを表示（「保存済み」と明示）。無ければ「いまはAIに接続できません。保存済みの質問を試してください。」 |
| `service_unavailable` | 503 | 回数を数える KV が使えない（通さずに止める） | 429 と同じ |
| `server_misconfigured` | 503 | `ANTHROPIC_API_KEY` か `IP_HASH_SECRET` が未設定 | 429 と同じ |
| `upstream_error` | 502 | 上流（Anthropic）が 200 以外、通信の失敗、本文が読めない | 429 と同じ |
| `not_found` | 404 | `/api/chat` 以外のパス | 汎用のエラー表示 |
| `method_not_allowed` | 405 | `POST`・`OPTIONS` 以外のメソッド（`allow` ヘッダー付き） | 汎用のエラー表示 |

- 上流が 200 のときは、上流の応答（`{ content, stop_reason, ... }`）をそのまま返します。
- 画面は、上の表にない 5xx も、ネットワークの失敗も、429 と同じ扱いにします。
- **毎回の要求には、約 11.8KB（11,801 バイト）の道具の定義が、Worker の側で付きます**（`TOOL_DEFS` を JSON にした大きさ）。画面は道具の定義を送らず、`messages` だけを送ります（ヘッダーは `content-type: application/json` だけ、`credentials: 'omit'`）。
- 下の上限（メッセージの件数・テキストの合計・本文のバイト数）は、画面が送る `messages` だけに掛かります。Worker が付ける道具の定義（約 11.8KB）は数えません。

### 会話の大きさの上限

1 回の要求には、次の 3 つの上限があります。どれか 1 つでも超えると Worker は断ります（`invalid_messages` か `body_too_large`）。

| 上限 | Worker の値 | 画面側が守る値（余裕を持たせてあります） |
|---|---|---|
| メッセージの件数 | 40 件 | 36 件 |
| テキストの合計（メッセージの文章・道具の入力・道具の結果・考えのブロックを数えます） | 48,000 文字 | 40,000 文字 |
| 本文の大きさ（UTF-8 のバイト数） | 64KB（65,536 バイト） | 56,000 バイト |

- 日本語は 1 文字が 3 バイトなので、実際には**バイト数の上限に先に届きます**（おおよそ 21,000 文字）。道具を 1 回呼ぶ質問は 4 件のメッセージになるので、件数の上限は質問 9〜10 回で届きます。
- 画面側（`src/ai/client.ts` の `ask()`）は、**要求を送る前に毎回**（道具の呼び出しの途中も、数字の言い直しの要求も）大きさを測り、超えるときは、`history` のいちばん古い「質問と答えのまとまり」を、まとまりごと捨てます（`tool_use` と `tool_result` の組を引き裂きません）。捨てたときは、結果に `trimmed: true` と `trimmedExchanges`（捨てたまとまりの数）が付きます。
- 履歴を全部捨てても、いまの質問（と、そこまでの道具のやり取り）だけで上限を超えるときは、要求を送らず、`status: 'unavailable'`・`needsNewConversation: true`・「会話が長くなりすぎました。新しい質問を始めてください。」を返します。

## 制限は「できるだけ」の仕組みです（Limits are best-effort）

1 日の上限（1 つの IP あたり 20 回、全体で 300 回。`DAILY_IP_LIMIT`・`DAILY_TOTAL_LIMIT` で変えられます）は、Workers KV の数え上げで実装しています。これは**防御の最後の砦ではなく、通常の使い方での目安**です。

- KV には「足し算を 1 回で行う」命令がなく、読んでから書く方式です。同時に届いた要求は同じ値を読んで互いの書き込みを上書きします（更新の取りこぼし）。
- そのため、短い間に集中した要求は**大きく少なく数えられます**。試験（`index.test.ts` の「best-effort」）で、1 つの IP あたり 3 回・全体 5 回の上限に対して 50 件の同時要求がすべて通ることを確かめています。「数件のずれ」ではありません。
- KV は反映が遅れることもあり（結果整合）、これも数え漏れの原因です。
- 害を小さくするため、書き込みは「全体 → IP」の順に 1 つずつ行い、全体の書き込みが失敗したら IP は数えません。KV が使えないときは通さずに 503 を返します（fail closed）。
- IP は HMAC-SHA-256（鍵は `IP_HASH_SECRET`）で変換して保存し、生のアドレスは保存しません。IPv6 は /64 の範囲で 1 人と数えます。

**お金の本当の上限は、API キーを持つ Anthropic ワークスペースの利用上限（spend limit）だけです。** `Origin` の確認も 1 日の回数の上限も、お金を確実に止める仕組みではありません。公開する前に必ず設定してください。

## 公開前のチェックリスト（承認を得てから）

公開（デプロイ）は本人の承認を得てから行います。勝手に実行しません。

- [ ] Anthropic のワークスペースに利用上限（spend limit）を設定した（最も大事な上限）
- [ ] `wrangler.jsonc` の `ALLOWED_ORIGINS` から `http://localhost:5173` を外し、公開ページの出どころ（例 `https://…pages.dev`）だけにした
- [ ] KV の名前空間を作り、`wrangler.jsonc` の `kv_namespaces[0].id` の仮の値を本物に置き換えた
- [ ] `wrangler secret put ANTHROPIC_API_KEY` で API キーを登録した（コードにも設定ファイルにも書かない）
- [ ] `wrangler secret put IP_HASH_SECRET` で長いランダムな文字列を登録した
- [ ] 別のベンダーによる第二の意見のレビュー（コードレビュー）を済ませた
- [ ] 公開後、公開ページから 1 回だけ実際に質問して動作を確かめた

## 設定

| 名前 | 種類 | 内容 |
|---|---|---|
| `ANTHROPIC_API_KEY` | 秘密 | Anthropic の API キー。応答にもログにも出しません。 |
| `IP_HASH_SECRET` | 秘密 | IP を変換する HMAC の鍵。未設定なら 503 `server_misconfigured`。 |
| `RATE_KV` | KV | 日ごとの数え上げ（キーは UTC の日付つき、2 日で消えます）。 |
| `ALLOWED_ORIGINS` | 変数 | 呼び出してよい出どころ（カンマ区切り）。 |
| `DAILY_IP_LIMIT` / `DAILY_TOTAL_LIMIT` | 変数（任意） | 既定は 20 / 300。`0` で全部止められます。 |

## ローカルでの確認

```sh
npx vitest run worker      # 試験（fetch と KV は偽物。実際の API は呼びません）
npm run typecheck          # worker/ と、共有する src/ai/toolDefs.ts を含めて型を確かめる
# 公開はせずに、共有ファイルを含めて 1 つにまとめられるかだけ確かめる（--dry-run）
WRANGLER_SEND_METRICS=false npx wrangler deploy --dry-run --outdir "$TMPDIR/wrangler-dry" -c worker/wrangler.jsonc
cp worker/.dev.vars.example worker/.dev.vars   # 手元で wrangler dev をするときだけ。.dev.vars と .dev.vars.* は git に入れません（.dev.vars.example だけ入っています）
```
