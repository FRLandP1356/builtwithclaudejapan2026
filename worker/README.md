# worker: Claude API の中継（Cloudflare Workers）

画面からの質問を Anthropic の Messages API に中継する小さな Worker です。API キーを画面側に置かないために使います。

公開先は、公開ページ自身の `/api/chat`（https://japan2100.pages.dev/api/chat）です。この Worker は公開の住所（workers.dev）を持たず（`workers_dev: false`）、公開ページの Cloudflare Pages Function（`functions/api/chat.ts`）が、サービスバインディング `CHAT_API`（リポジトリのルートの `wrangler.jsonc`）で内部から呼びます（2026-11-06 に公開し、同日に今の形にした）。呼び出してよい出どころは、公開ページの https://japan2100.pages.dev だけです。

## できること

- `POST /api/chat` だけを受け付けます（それ以外のパスは 404、他のメソッドは 405）。
- 本文は `{ "messages": [...] }` だけです。`messages` は、確かめた項目から作り直して送ります（余分な項目、ブロックの `cache_control`、画像や文書のブロックは届きません）。**ただし `tool_use` ブロックの `input` だけは作り直しません。** JSON のオブジェクトであれば、入れ子の項目も含めて、受け取ったとおりに上流へ送ります。長さはテキストの合計（48,000 文字）の枠に数えるだけで、その道具の入力の形に合っているかは確かめません（`validate.test.ts` が、そのまま通ることを確かめています）。
- 上流への要求は、次のとおり Worker が決めます。画面から来た値は使いません。**上流の要求の本体とヘッダーは、定数と、確かめた `messages` と、道具の定義だけから作ります**（`index.test.ts` が、本体全体とヘッダー全部を完全一致で固定しています）。
  - モデル `claude-sonnet-5-5`、`max_tokens` は 3000、`output_config: { "effort": "low" }`、`thinking: { "type": "adaptive", "block_binding": { "prefix_mismatch_behavior": "drop_block" } }`。
  - システムプロンプトは `cache_control: { "type": "ephemeral" }` を付けた 1 つのブロックです。これで道具の定義とシステムプロンプト（毎回同じ。2026-11-06 の実測は 5,941 トークン、システムの指示と道具の説明を直した再デプロイのあとは 5,989 トークン、書式の規則を足した再デプロイのあとは 6,078 トークン。以前の見積もりは約 4,600）が、**直前の呼び出しから 5 分以内に次の呼び出しがあるとき**、割引の読み出し価格（入力の 10%）になります。間が空くと（キャッシュは 5 分で切れ、使うたびに延びます）毎回キャッシュの書き込み価格（入力の約 1.25 倍）になり、そのときは使わないより少しだけ高くつきます（約 4,600 トークンで 1 回あたり 0.002 ドルほど）。
  - システムの指示（`worker/systemPrompt.ts`）には、勧めない・「予測」と書かない・「残せない」と書かない、といった決まりのほかに、書式の規則があります（2026-11-06 に足した）。画面はモデルの出力を文字のまま表示するので、表（縦線の「|」）、太字や斜体の記号（「**」「*」）、見出しの記号（「#」）は使わず、箇条書きは行頭の「- 」だけにして、入れ子にしません。足す前は、モデルが表や太字を使い、画面では記号がそのまま見える答えがありました。
  - ヘッダーは `x-api-key`・`anthropic-version: 2023-06-01`・`anthropic-beta: thinking-binding-controls-2026-08-01`・`content-type` の 4 つだけです。
  - 理由（Claude API の公式ドキュメントで確かめた内容。2026-11-06）: `thinking` を省くとこのモデルは適応的な思考で動き、思考のトークンも `max_tokens` に数えるため、1500 では答えが途中で切れたり空になったりします。画面は署名つきの思考ブロックを含む過去のやり取りを送り返し、古いやり取りを捨てます。思考ブロックは、システムプロンプト・道具・それより前のメッセージが変わっていない間だけ有効で、2026-08-31 以降に作られたアカウントでは、捨てたあとの再送が 400 になります。`block_binding` の `drop_block` は、一致しない最初のブロックとそれ以降をその要求だけ API が落とし、要求は成功します。これにはベータヘッダーが要り（無いと `block_binding` が 400）、`type: "adaptive"` のときだけ使えます。`output_config.effort` は正式版で、ベータヘッダーは要りません（トップレベルではなく `output_config` の中です）。
  - 上流の応答は書き換えません。`stop_reason`（`end_turn`・`max_tokens`・`refusal`・`tool_use` など）も `content` も、そのまま返します。
  - 道具の定義（名前・説明・入力の形）の正本は `src/ai/toolDefs.ts` の `TOOL_DEFS` です。画面側の `src/ai/tools.ts`（道具の実装）と Worker が、この 1 つのファイルを共有します。Worker は毎回、この定義をそのまま Claude に送ります。
  - 本文に `tools`（やそのほか知らない最上位の項目）があっても、**無視します**（エラーにはしません。送られた値は一切、上流に届きません）。
  - 過去のやり取りに入る `tool_use` ブロックの道具名は、`TOOL_NAMES`（同じファイルから出る名前の一覧）にあるものだけです。ないものは 400 `invalid_messages` です。
  - 説明は 400 文字未満、入力の形（JSON にした長さ）は 2,000 文字未満に収めます（上流への要求を小さく保つため。`toolDefs.test.ts` が確かめます）。
- 本文は 64KB まで（超えると 413）。メッセージは 40 件まで、テキストの合計は 48,000 文字までです。
- 応答は上流が 200 のときだけそのまま返します。上流が 200 以外（4xx も含む）、ネットワークの失敗は、中身を見せずに 502 `{ "error": "upstream_error" }` です。上流への呼び出しは `redirect: 'manual'` なので、3xx（リダイレクト）は追いかけず、同じ 502 になります（Cloudflare の `fetch` は `follow` と `manual` だけを受け付けます。標準の `error` は workerd で TypeError になり、すべての呼び出しが失敗します。手元の workerd で、`error` は TypeError、`manual` は 302 をそのまま返す、を確かめました）。
- すべての応答に `x-content-type-options: nosniff` を付けます。
- 呼び出せる出どころは `ALLOWED_ORIGINS`（カンマ区切り、完全一致）だけです。`Origin` が無い、または違う場合は 403 で、**この 403 の応答には CORS のヘッダー（`access-control-allow-origin` など）を付けません。** そのため、他のウェブサイトのページの中のブラウザは応答を読めず、「403」ではなく通信の失敗として受け取ります。**これは認証ではありません。** 他のウェブサイトのページの中からブラウザ経由でこの Worker を使わせない、という程度の仕組みです。`curl` などのブラウザ以外の道具は `Origin` に好きな値を付けられるので、これでは止まりません。

## 応答コード（Response codes）

エラーの応答の本文は `{ "error": "<コード>" }` です（429 だけ `"cached": true` が付きます）。コードと HTTP ステータスは `worker/index.ts` と `worker/validate.ts` のとおりです。画面側の動きは `src/ai/client.ts` の `ask()` が決めています。

| コード | HTTP | 意味 | 画面の動き |
|---|---|---|---|
| `invalid_body` | 400 | 本文が JSON のオブジェクトではない（配列や文字列など） | 汎用のエラー表示。画面は常に `{ messages }` を送るので、通常は起きません |
| `invalid_json` | 400 | 本文が JSON として読めない | 同上 |
| `invalid_messages` | 400 | `messages` が無い・空・41 件以上、テキストの合計が 48,000 文字を超える、またはブロックの形・道具名が決まりに合わない | 同上。会話が長くなると起きうるので、画面側は送る前に大きさを測って防ぎます（下の「会話の大きさの上限」） |
| `body_too_large` | 413 | 本文が 64KB（UTF-8 のバイト数）を超えた。日本語は 1 文字が 3 バイトなので、長い会話ではテキストの合計が 48,000 文字に届く前に、およそ 21,000 文字でこの上限に先に届く | 「質問が長すぎます。」。画面側は、送る前に大きさを測り、古いやり取りを自動で捨てるので、通常は届きません（下の「会話の大きさの上限」） |
| `origin_not_allowed` | 403 | `Origin` ヘッダが許可リストに無い、または付いていない。この応答には CORS ヘッダーが付かない（404・405 も同じ） | **ブラウザには 403 として届かず、通信の失敗に見える**（応答を画面に渡さないため）。画面は通信の失敗を 429 と同じ扱いにする（`src/ai/client.ts` の `transportFailure`）。つまり、公開ページの出どころを `ALLOWED_ORIGINS` に入れ忘れると、画面には「いまはAIに接続できません」と出て、原因が分かりにくい。ブラウザの開発者ツール（ネットワークとコンソール）で確かめる |
| `rate_limited` | 429（`cached: true` 付き） | 短時間の連続（IP ごとに 60 秒で 20 回、`IP_LIMITER`）、または 1 日の回数の上限（IP ごとに 60 回、または全体で 400 回）に達した | 同じ質問の、確認済みの保存済みの答えがあればそれを表示（「保存済み」と明示）。無ければ、確認済みの保存済みの答えを持つ質問が1つでもある間は「いまはAIに接続できません。保存済みの質問を試してください。」、1つもない間（2026-11-06 から、5件とも確認済みなので、いまはこちらにはなりません）は「いまはAIに接続できません。時間をおいて、もう一度お試しください。」 |
| `service_unavailable` | 503 | 回数を数える KV を読めない、または保存できない（同じ区分・同じ IP のキーに 1 秒以内に 2 回書くとき、無料プランの書き込みの枠切れなど）、または `IP_LIMITER` の呼び出しが失敗した（いずれも通さずに止める。上流は呼ばない） | 429 と同じ |
| `server_misconfigured` | 503 | `ANTHROPIC_API_KEY`・`IP_HASH_SECRET` のどちらか、または `IP_LIMITER` のバインディングが未設定（黙って飛ばさない） | 429 と同じ |
| `internal_error` | 500 | 想定外の失敗（たとえば、アップロードの途中で接続が切れて本文を読めなくなった）。Worker が自分で作る応答で、`nosniff` と本文はほかの応答と同じ形（CORS ヘッダーは付けない）。ログには `unexpected error` の 1 行だけ。何も数えない | 429 と同じ |
| `upstream_error` | 502 | 上流（Anthropic）が 200 以外、通信の失敗、本文が読めない | 429 と同じ |
| `not_found` | 404 | `/api/chat` 以外のパス | 画面が「Worker が無い」と読む（最初の答えが返る前なら「このバージョンでは、AIへの質問は使えません…」、答えが返ったあとなら 429 と同じ）。画面は正しいパスにしか送らないので、起きるのは接続先の設定の間違いのとき。Worker は 404・405 を、この用途以外には使わない |
| `method_not_allowed` | 405 | `POST`・`OPTIONS` 以外のメソッド（`allow` ヘッダー付き） | 404 と同じ |

- 上流が 200 のときは、上流の応答（`{ content, stop_reason, ... }`）をそのまま返します。
- 画面は、上の表にない 5xx も、ネットワークの失敗も、429 と同じ扱いにします。
- **毎回の要求には、約 11.8KB（11,801 バイト）の道具の定義が、Worker の側で付きます**（`TOOL_DEFS` を JSON にした大きさ）。画面は道具の定義を送らず、`messages` だけを送ります（ヘッダーは `content-type: application/json` だけ、`credentials: 'omit'`）。
- 下の上限（メッセージの件数・テキストの合計・本文のバイト数）は、画面が送る `messages` だけに掛かります。Worker が付ける道具の定義（約 11.8KB）は数えません。

### 会話の大きさの上限

1 回の要求には、次の 3 つの上限があります。どれか 1 つでも超えると Worker は断ります（`invalid_messages` か `body_too_large`）。

| 上限 | Worker の値 | 画面側が守る値（余裕を持たせてあります） |
|---|---|---|
| メッセージの件数 | 40 件 | 36 件 |
| テキストの合計（メッセージの文章・道具の入力・道具の結果・考えのブロックを数えます） | 48,000 文字 | 40,000 文字 |
| 本文の大きさ（UTF-8 のバイト数） | 64KB（65,536 バイト） | 56,000 バイト |

- 日本語は 1 文字が 3 バイトなので、実際には**バイト数の上限に先に届きます**（おおよそ 21,000 文字）。道具を 1 回呼ぶ質問は 4 件のメッセージになるので、件数の上限は質問 9〜10 回で届きます。
- 画面側（`src/ai/client.ts` の `ask()`）は、**要求を送る前に毎回**（道具の呼び出しの途中も、数字の言い直しの要求も）大きさを測り、超えるときは、`history` のいちばん古い「質問と答えのまとまり」を、まとまりごと捨てます（`tool_use` と `tool_result` の組を引き裂きません）。捨てたときは、結果に `trimmed: true` と `trimmedExchanges`（捨てたまとまりの数）が付きます。
- 履歴を全部捨てても、いまの質問（と、そこまでの道具のやり取り）だけで上限を超えるときは、要求を送らず、`status: 'unavailable'`・`needsNewConversation: true`・「会話が長くなりすぎました。新しい質問を始めてください。」を返します。

## 制限の仕組みと限界（数えられないときは止まります）

制限は 3 層あります。**1 日の回数と短時間の連続は、通常の使い方での目安で、お金を確実に止める仕組みではありません。** その代わり、**数えられなくなったら止まります**（読み取りも書き込みも、失敗したら要求を断る。作者の指摘を受けた進行役の裁定。台帳の裁定 38）。

1. **短時間の連続（`IP_LIMITER`）**: Workers の Rate Limiting バインディングで、1 人（IP を HMAC で変換した値）あたり 60 秒に 20 回。超えると、1 日の上限と同じ 429 `{ "cached": true, "error": "rate_limited" }` を返し、KV は読み書きしません。`limit()` 自体が失敗したら、通さずに 503 `service_unavailable` です。このバインディングは Cloudflare の拠点ごとに数え、結果整合で、概算の制限として説明されている（正確な集計の仕組みではない）、取りこぼしを許す仕組みです（Cloudflare の資料は IP をキーにするのを勧めていませんが、このアプリには利用者の ID が無いため、IP を HMAC で変換した値を使います。携帯回線などで IP を共有する人は、まとめて数えられます）。
2. **1 日の回数（Workers KV）**: **上流への呼び出しの回数**で数えます（質問の回数ではありません。1 つの質問で、道具を呼ぶたびに上流を呼ぶので、最大 9 回まで使います）。1 つの IP あたり 60 回、全体で 400 回が既定です（`DAILY_IP_LIMIT`・`DAILY_TOTAL_LIMIT` で変えられます。`0` で全部止められます）。確認用の 95 回の質問は、合計 231 回の呼び出し（235 回のうち、残りの 4 回はトークン数を測る質問）で、1 つの質問あたり平均 2.43 回でした。この平均なら、全体の 400 回は約 165 問分（400 ÷ 2.43）、1 つの IP の 60 回は約 25 問分です。確認用の質問の平均で、利用者の質問の平均ではありません。数え方は次の節です。
3. **お金の本当の上限**: API キーを持つ Anthropic ワークスペースの利用上限（spend limit）だけです。

### 1 日の回数の数え方と限界

- KV には「足し算を 1 回で行う」命令がなく、読んでから書く方式です。同時に届いた要求は同じ値を読んでから書くので、上限の判定を一緒に通ります（読み取りと書き込みの間の競合）。KV は反映が遅れることもあり（結果整合）、これも数え漏れの原因です。
- **KV は同じキーへの書き込みを 1 秒に 1 回までしか受け付けません**（1 秒以内の 2 回目は 429 で断られる）。全体の数は 1 つのキーでは 1 秒に 1 回しか数えられないので、**16 個のキーに分けています**。
  - キーは `total:<UTC の日付>:<0〜15>`。どれに書くかは、その人の HMAC の先頭 1 バイトを 16 で割った余りで決まります（同じ人はいつも同じ区分に書きます。人は区分に均等に散ります）。上限の判定は、**16 個の合計**で行います。
  - 1 回の判定で、IP のキーと 16 個の区分を一緒に読みます（KV の読み取り 17 回。順番にではなく、同時に出す。`rateLimit.test.ts` が確かめています）。**1 つでも読めなければ通さずに 503**（fail closed。数が読めないと上限を守れないため）。
  - **書き込みも fail closed です。** その人の区分と IP のキーの 2 つを**同時に**保存し、両方の結果を待ちます。**どちらか 1 つでも保存できなければ、要求は 503 `service_unavailable`（読み取りの失敗と同じ形）で断り、上流（Claude）は呼びません。** ログは `rate limit store unavailable` の 1 行です（読み取りの失敗と同じ固定の文字列。キーも IP もエラーの中身も含めない）。片方だけ保存できたときは、そのカウンターが、呼び出されない 1 回ぶん多くなります（断る側に倒れる。巻き戻さず、2 日で消える）。
  - **遅くなります。** Workers は、応答のヘッダーを待つ接続を 1 つの呼び出しで 6 本までしか同時に持てず（7 本目からは待たされる。Cloudflare の資料）、17 回の読み取りは約 3 回分の KV の往復になります。上流（Claude）を呼ぶ前に、その分の時間が毎回足されます（2026-11-06 に測った値は、この節ではなく、下の「実測」の節。上流を含む 1 回の応答は、中央値 2.3 秒、最大 5.9 秒で、KV の読み取りを含みます）。読み取りには `cacheTtl` を付けていません（付けると、ほかの拠点の数が遅れて見えます。付いていないことを同じ試験が確かめています）。
  - **保存された値が数字でない・負・無限大のときは 0 として数えます。これだけは、数えられない値でも止めない例外です。** そうしないと、1 つの壊れた値で合計が NaN になり、上限の判定（`NaN >= 400` は偽）が効かなくなるためです。Worker は整数しか書かないので、これは壊れたときの備えで、通常は起きません。止めない側に倒したのは、壊れたキーが消える 2 日後まで AI 全体が止まるのを避けるためで、そのキーの数え落としと引き換えです。次にその区分へ書くときに、正しい値で上書きされます。とても大きな数は有限なので、そのまま数えます（断る側に倒れる）。
- IP は HMAC-SHA-256（鍵は `IP_HASH_SECRET`）で変換して保存し、生のアドレスは保存しません。IPv6 は /64 の範囲で 1 人と数えます。**ただし、IPv6 の /48 を持つ人（無料のトンネル業者や多くの VPS が配る）は、/64 を 65,536 個使えるので、65,536 人と数えられます。** 人ごとの制限（短時間の連続も 1 日の回数も）は、その気になった相手を止められません。効くのは全体の上限とワークスペースの利用上限だけです。

**ときどき「あとでもう一度」が出ます。** 保存できない要求は断るので、同じカウンターへ 1 秒以内に 2 回書こうとした要求は、2 回目が 503 になります（画面は 429 と同じ「いまはAIに接続できません」の扱いです）。
- 同じ人（同じ IP）が 1 秒以内に 2 回呼ぶと、2 回目が断られます。ふつうの質問は 1 回の呼び出しに数秒かかるので、まれです。**同じ IP を共有する人（会場の Wi-Fi など）は、その IP 全体で、1 秒に 1 回しか数えられません。**
- 全体の区分は 16 個なので、**全体で 1 秒に通せるのは最大 16 件**です。人が 16 の区分に散ると、全体で 1 秒に 1 件のペースで約 6%、2 件で約 11%、5 件で約 24%、16 件で約 50% の要求が、同じ区分の直前の書き込みに当たって断られます（リポジトリには入れていない乱数のシミュレーション、IP のキーは含めず。測定ではなく見積もり）。
- 有料プランでも、この 1 秒に 1 回の制限は同じです（プランで外れるのは、下の 1 日の書き込みの枠だけ）。

**同時に届いたときの超過。** 1 つの波（N 件の要求が、全員が書き込みの前に読み終えるように重なる）では、全員が同じ値を読んで上限の判定を通ります。しかし、KV は同じキーへの 2 回目の書き込みを断り、保存できなかった要求は断られる（503）ので、**通るのは各区分の最初の 1 件だけ（最大 16 件）**です。したがって、上限をまたぐ波が超える量は、最大 15 件（区分の数 − 1）です。次の表は、`rateLimit.test.ts` の決まった計算（固定した HMAC の鍵とアドレス、同じキーへの 1 秒以内の 2 回目の書き込みは KV と同じく断り、断られた要求は通らない）が、上限 400 に対して、上限で断られる波が出るまでに通した呼び出しと、503 で断られた要求の数です。**表の数字はテストが完全一致で固定しています**（前提が変わったら、テストと表を一緒に直す）:

| 攻撃の形（モデル） | 通った呼び出し（上限 400） | 超過 | 503 で断られた要求 | 最悪の 1 回（約 0.17 ドル）で換算 |
|---|---|---|---|---|
| 1 件ずつ順番に届く | 400 | 0 | 0 | 約 68 ドル |
| 毎回新しい人 5 件の波、1 秒に 1 回 | 403 | +3 | 52 | 約 69 ドル |
| 同 10 件 | 402 | +2 | 118 | 約 68 ドル |
| 同 20 件 | 409 | +9 | 291 | 約 70 ドル |
| 同 50 件 | 403 | +3 | 897 | 約 69 ドル |
| 同 50 件の波を 0.2 秒ごと（1 秒に 5 回） | 400 | 0 | 5,800 | 約 68 ドル |
| **1 人**が 20 件ずつ同時に、1 秒に 1 回（その人の上限 60 に届くまで） | 60 | 0（その人の上限 60 で止まる） | 1,140 | 約 10 ドル |
| 新しい人が毎回現れ、各自が 20 件ずつ同時に（全体の 400 に届くまで） | 400 | 0 | 7,600 | 約 68 ドル |

- 超過が小さいのは、数えられなかった要求を通さないからです。**代わりに、同時に届いた要求の大半が 503 で断られます**（50 件の波では約 35 件が断られる）。
- 表の前提: 1 つの拠点で、書き込みがすぐ見え、波は表のとおりの間隔で来る、というモデルです。**拠点が複数あると、反映が最大 60 秒ほど遅れ、別の拠点の書き込みを読めないまま通る要求が出るので、超過が表より大きくなりえます**（その量は測っていません）。
- 同じ人の同時の呼び出し（表の下の 2 行）は、同じ IP のキーと区分を取り合うので、1 秒に 1 件しか通りません。`IP_LIMITER` も 1 つの拠点で 60 秒に 20 回までです。

**超過のお金への影響**: 通った呼び出しの数 × 最悪の 1 回（下の見積もりで約 0.17 ドル）です（上の表の右の列）。モデルの範囲では、1 日の合計は 415 回（上限 400 ＋ 15）を超えず、約 71 ドル分までです。ただし、拠点が複数あるときの超過は測っていないので、これは保証ではありません。**止めるのはワークスペースの月の利用上限（約 100 ドル）だけです。**

**（2026-11-06 に、作者は Workers の有料プラン（Paid）に切り替えました。請求画面に「Workers Paid」、2026-11-21 に更新と出ています。次の段落は、無料プランのままだった場合の説明で、今は当てはまりません。お金の側の備えは「請求の安全」の節。）** **Workers の無料プランでは、約 500 回数えたところで AI が止まります。** KV の無料プランは、アカウント全体で 1 日に書き込み 1,000 回まで、読み取り 100,000 回までです（毎日 00:00 UTC にリセット）。通した 1 回の呼び出しで 2 回書くので、約 500 回で書き込みの枠が尽きます。尽きたあとの書き込みは失敗し、**保存できない要求は断る**ので、00:00 UTC まで AI は 503 を返し続けます（上流は呼ばないので、お金は使いません）。**有料プラン（Paid）ならこの枠が無く、この停止は起きません**（プランを確かめる。チェックリストの手順 2。2026-11-06 の時点で、公開した Worker のプランは確かめられていない）。同じアカウントのほかの Worker の分もこの枠に入ります。読み取りは 1 回の判定で 17 回なので、無料プランでは約 5,800 回で尽きますが、書き込みの枠のほうが先に尽きます。ただし、コードの全体の上限（既定の 400 回）はこの約 500 回より低いので、同じアカウントのほかの用途で枠を使わない限り、先に当たるのは全体の上限です。作者は、全体 400 回・1 人 60 回を決めました（2026-11-06）。プランは、そのあと有料に切り替えました（上）。

**お金の本当の上限は、API キーを持つ Anthropic ワークスペースの利用上限（spend limit）だけです。** Worker の数え上げ（`IP_LIMITER` も、KV の 1 日の回数も）は、読み取りと書き込みの間の競合や、拠点ごとの反映の遅れがあり、お金を確実に止める仕組みではありません（数えられないときに止まるのは、その分の無駄を減らすためです）。`Origin` の確認も同じです。公開する前に必ず設定してください。

## お金の見積もり（Spend estimate）

前提（置いた仮定です。計算は 2026-11-06 の朝の時点で、手順 9 の前。手順 9 で測った値は、この節の最後の「実測」にあります）:

- Sonnet 5.5 の料金: 入力 100 万トークンあたり 2 ドル、出力 10 ドル、キャッシュの読み出し 0.20 ドル（書き込みは 5 分のもので 2.50 ドル）。
- **入力の上限は、本文の大きさ（64KB）から取ります。** 1 つの要求の `messages` は 64KB（65,536 バイト）を超えられないので、**1 バイトを 1 トークンまで**と置くのを、考えられる上限とします（めずらしい文字や意味のない文字列は、1 バイトに近い数のトークンになりえます。トークナイザの仕組みは公開されていないため、これも仮定です）。これに、毎回付く道具とシステムプロンプトの約 4,600 トークン（見積もり）を足します。以前の見積もり（テキストの上限 48,000 文字を 1 文字 1 トークン）は上限になっていませんでした。混ぜた文字や、わざと作った文字列が 48,000 トークンを超えうるためです。
- 出力は `max_tokens` の 3,000 トークン（思考のトークンを含みます）。
- キャッシュの割引は使いません。割引は、直前の呼び出しから 5 分以内に次の呼び出しがあるときだけ効きます。間が空くと書き込み価格（入力の約 1.25 倍）になり、約 4,600 トークンで +0.002 ドルほどです。

**最悪の 1 回**: 入力 (65,536 + 4,600) = 70,136 トークン × 2 ドル/100 万 = 0.140 ドル、出力 3,000 トークン × 10 ドル/100 万 = 0.030 ドル、合計 **約 0.17 ドル**。1 つの質問が最大 9 回の呼び出しを使っても、1 回ごとの入力はこの上限に収まるので、「1 回の上限 × 回数」で上から押さえられます。

| 数え方 | 回数 | 最悪の合計（全部が最悪の 1 回だったとして） |
|---|---|---|
| 1 人（IP）あたり（`DAILY_IP_LIMIT` 60） | 60 回 | 約 10 ドル（0.170 × 60 ＝ 10.2） |
| 全体の 1 日（`DAILY_TOTAL_LIMIT` 400） | 400 回 | 約 68 ドル（0.170 × 400 ＝ 68.1） |

最悪の 1 日が約 68 ドルなので、ワークスペースの月の利用上限（約 100 ドル）は、最悪の 1 日が 1.5 日分続くと尽きます（100 ÷ 68.1 ≒ 1.47）。

**日本語だけの会話なら、もっと小さくなります**: 本文の 64KB の上限で、日本語（1 文字が 3 バイト）は約 21,000 文字までです。1 文字 1〜1.5 トークンと置くと、入力は約 25,600〜36,100 トークンで、最悪の 1 回は約 0.08〜0.10 ドルです（日本語のトークン数の比率は、手順 9 で測りました。下の「実測」）。**ふつうの使い方**の目安（仮定: 新しい入力 3,000 トークン、キャッシュ読み出し 4,600 トークン、出力 1,000 トークン、5 分以内に続けて使う）は 1 回 約 0.017 ドルで、400 回で約 7 ドルです。

**これは Worker の数え上げが働いた場合の上限です。** 数え上げは目安で、同時に届いた要求は上限の判定を一緒に通りますが、保存できなかった要求は断られるので、上限を超える量は小さく抑えられます（上の表のモデルで、1 日の合計は最大 415 回、約 71 ドル分）。ただし、拠点が複数あるときの超過は測っていないので、1 日に 68 ドルや 71 ドルは保証された上限ではありません。**お金を確実に止めるのは、ワークスペースの月の利用上限（約 100 ドル）だけです**。尽きると上流が 4xx を返すようになり、Worker は 502 を返します（画面は 429 と同じ扱いにします）。ワークスペースには、利用上限のほかに、毎分のリクエスト数と入力トークン数のレート制限も設定します（チェックリストの手順 1）。これは Worker では作れない、サーバー側で一括して効く速度の上限です。

### 実測（2026-11-06）

公開した Worker に実際の質問を 235 回送って測った値です（方法と内訳は [docs/ai-live-check.md](../docs/ai-live-check.md)。すべて HTTP 200）。上の見積もりは書き換えず、測った値をここに並べます。

- 毎回付く道具とシステムプロンプトの部分: 5,941 トークン（見積もりは約 4,600）。システムの指示と道具の説明を直した再デプロイのあとは 5,989 トークン。
- 一言の質問は、入力の合計が 6,023 トークン。20,000 文字（本文 49,506 バイト、うち ASCII 以外が 14,463 文字）の質問は 23,302 トークンで、質問の分は 17,279 トークンです。1 文字あたり 0.86、ASCII 以外の文字だけで割ると 1.19、本文の 1 バイトあたり 0.35。上の「1 バイトを 1 トークンまで」の仮定は、この測定の約 2.9 倍で、上限として働いています。
- 固定部分を 5,941 トークンにして最悪の 1 回を計算し直すと、入力 (65,536 + 5,941) = 71,477 トークン × 2 ドル/100 万 = 0.143 ドル、出力 0.030 ドルで、合計 約 0.173 ドルです。400 回で約 69 ドル、60 回で約 10.4 ドル、415 回で約 72 ドル。上の表と文の数字（約 0.17 ドル、約 68 ドル、約 71 ドルなど）は見積もり時の計算で、2% 以内で上に動きます。
- 実際の平均は、1 回の呼び出しあたり約 0.008 ドル（235 回で約 1.80 ドル。使った量から計算した見積もり。最初の 161 回では、Anthropic の Console の残高の減りは約 1.17 ドルで、見積もりの 1.18 ドルと合いました）。400 回で約 3 ドルになる計算です。上の「ふつうの使い方」の目安（1 回 約 0.017 ドル、400 回で約 7 ドル）は 1 回の呼び出しとしては高めで、1 つの質問の費用（1〜4 回の呼び出しの合計、約 0.02 ドル）に近い値でした。
- キャッシュ: 235 回のうち 233 回が読み出しでした（書き込みは、最初の呼び出しと、再デプロイのあとの最初の呼び出し）。5 分を超えて間があいた場合は試していません。
- 呼び出しの数と容量: 95 回の質問は合計 231 回の呼び出しで、1 つの質問あたり平均 2.43 回でした（1 回が 9 問、2 回が 42 問、3 回が 38 問、4 回が 6 問）。全体の 400 回は約 165 問分、1 つの IP の 60 回は約 25 問分です（確認用の質問の平均）。
- 書式の規則を足したあとの作り直し: 保存済みの答え 5 件を作り直した 13 回（約 0.07 ドル、すべて HTTP 200、`stop_reason` は `tool_use` 7・`end_turn` 6）。毎回付く部分は 6,078 トークンで、最初の呼び出しが書き込み、残りの 12 回が読み出しでした。この 13 回は、上の 235 回に含めていません。
- 応答時間: 1 回の呼び出しは、この Mac から測って、中央値 2.3 秒、最大 5.9 秒（KV の読み取りを含む）。1 つの質問は、呼び出し 1〜4 回の合計で 2.9〜12.2 秒（中央値 5.6 秒）でした。

## 請求の安全（Billing safety）

**Cloudflare には、使った金額が上限に達したら自動で止まる設定（ハードキャップ）がありません**（2026-11-06 に公式ドキュメントで確認）。「予算アラート」は通知だけで、止めません。クレジットを先に買っておいて、尽きたら止まる形も、確かめた範囲では見つかりませんでした（Workers は、月額の定額と、使った分の従量払いです）。そのため、請求を抑えるのは、次の 4 段（Cloudflare の通知・1 回あたりの上限・Worker の数え上げ・お金の元の上限）の組み合わせです。

| 段 | 設定 | 何が起きるか |
|---|---|---|
| 1. Cloudflare の予算アラート | 1・5・10 ドル（10 ドルは自動で作られたもの）・20 ドル。宛先は Cloudflare のアカウントのメール | 月の使った金額（Billable Usage）が超えたらメールが来る。**止めはしない。** 画面の「Nov 2026 の支出」は、設定した時点で 0.00 ドル（月額 5 ドルの定額が、この支出に数えられるかは確かめていない） |
| 2. 1 回の呼び出しの上限 | `wrangler.jsonc` の `limits`: `cpu_ms` 100、`subrequests` 60（`wranglerConfig.test.ts` が固定） | 1 回の処理が使える CPU 時間と外への呼び出しの数を、通常の呼び出し（数 ms、約 21 回）の数倍に抑える。止まるのは、1 回の暴走だけ。呼び出しの数そのものは減らさない |
| 3. Worker の数え上げ | 1 日 400 回・1 人 60 回・1 人 60 秒に 20 回（`DAILY_*` と `IP_LIMITER`） | 数えられないときは断る（503）。目安であり、確実な止めではない（「制限の仕組みと限界」） |
| 4. Anthropic のワークスペース | 月の利用上限（約 100 ドル）、25 ドルでのメール通知、毎分のレート制限 | **お金の元（API の利用料）を確実に止める唯一の上限。** 尽きると上流が 4xx を返し、AI が止まる |

Workers の有料プランに含まれる量（KV の読み取り月 1,000 万回、書き込み月 100 万回）は、この Worker の想定（1 日 400 回、1 回の判定で読み取り 17 回・書き込み 2 回。月に読み取り約 20 万回、書き込み約 2 万 4 千回）の約 40 倍あります。Worker 自体の費用は、想定の範囲では、ほぼ定額の 5 ドルのはずです。大きく動くのは、Anthropic の利用料（段 4 が止める）です。

**すぐ止める方法**（上から順に、軽い順）:

1. AI だけを止める: `npx wrangler deploy -c worker/wrangler.jsonc --var DAILY_TOTAL_LIMIT:0`。以降の質問は、上流（Anthropic）を呼ばずに断られる（お金が出ない）。**戻すときは `--var` なしでもう一度 `npx wrangler deploy -c worker/wrangler.jsonc`**。
2. API キーを無効にする: Anthropic のコンソールで、このワークスペースのキーを無効にする（キーは有効期限 2026-12-06。無効にすると、Worker が上流から 4xx を受けて 502 を返す）。
3. Worker ごと止める: `npx wrangler delete -c worker/wrangler.jsonc`（Worker が無くなる。戻すには、手順 5 の秘密の登録と手順 7 の再デプロイが要る）。
4. 使っているクレジットカードに、使える額の上限や通知を付ける（カード会社の設定。Cloudflare 側の上限ではない）。

**気をつけること**: アラートのメールは、月の金額が超えてから届きます（遅れることがあります）。そのため、メールが来たら、まず「すぐ止める方法」の 1 を実行して、原因を調べます。

## ログ（記録されるもの）

`worker/wrangler.jsonc` で Workers Logs を有効にしてあります。記録の対象は、Worker 自身の `console` の出力だけにしてあります。リクエストごとに自動で出る「invocation logs」（URL・ヘッダー・接続元などの詳細）は切ってあり（`invocation_logs: false`）、トレースも使わず、サンプリングは 100%（`head_sampling_rate` 1）です。`wranglerConfig.test.ts` が、この設定を固定しています。

**Worker が書くのは、次の固定の文字列だけです。** どの行も、`console` の呼び出し 1 回につき、固定の文字列 1 つで、ほかの引数（Error・API キー・接続元の IP・状態を表す文・リクエスト ID・ヘッダー・上流の本文）は付きません。`index.test.ts` の「console output」の表が、すべての経路（何も書かない経路を含む）について、`console` の呼び出しの一覧を完全一致で確かめます（API キーが入っていても IP が入っていても、別の秘密や `IP_LIMITER` が欠けていても同じ）。さらに、ソースの中の `console` の呼び出しがちょうど 8 か所で、引数の書き方も決まったとおりであることも確かめます。

**ただし、Cloudflare が記録するときに、それぞれの行へ自分のメタデータ（スクリプト名・時刻など）を付けることがあります。何が付くかは、この環境の外では確かめられません。** そのため、「記録された行に接続元の IP や API キーが入らない」ことは、公開前チェックリストの手順 9 で、実際に記録された 1 行をダッシュボードで開いて確かめます（2026-11-06 の時点で、この確認は行っていません）。

| 行 | 意味 |
|---|---|
| `burst limiter unavailable` | `IP_LIMITER` の呼び出しが失敗した（503 で止めた） |
| `rate limit store unavailable` | 1 日の回数を KV から**読めなかった、または保存できなかった**（どちらも 503 で止めた）。**多いなら、AI が止まっている**（無料プランの書き込みの枠切れ、同じ区分への集中、KV の障害） |
| `server configuration missing: <名前>` | 秘密か `IP_LIMITER` が未設定（名前だけ。503） |
| `upstream request failed` / `upstream responded <状態>` / `upstream body unreadable` / `upstream body rejected` | 上流の失敗（502）。状態の数字だけ |
| `unexpected error` | 想定外の失敗（500） |

見るには、ダッシュボードの Workers Logs か、`npx wrangler tail -c worker/wrangler.jsonc` を使います。

**手順 9 の結果。** 済んだ項目（235 回の呼び出し、すべて HTTP 200）:

- 8 つの道具の定義がすべて受け付けられ、8 つともモデルが呼んだ。
- 道具を呼ぶやり取り（`tool_use`、`tool_result`、答え）が通った。

- `usage` と `stop_reason`: キャッシュの読み出しが 235 回のうち 233 回、`stop_reason` は `tool_use` と `end_turn` だけ（`max_tokens` と `refusal` は 0 件）、出力は最大 578 トークン。1 回の応答時間は、中央値 2.3 秒、最大 5.9 秒。

済んでいない項目:

- 429 の経路（`DAILY_IP_LIMIT` を 3 にして 4 回目で 429 になることの確認）。再デプロイが要るため省いた。
- 回答を断る（`refusal`）質問。
- Workers Logs で、記録された 1 行を開いて、接続元の IP と API キーが入っていないことの確認。

確認のあいだ、1 日の上限を一時的に引き上げた（`--var` で `DAILY_IP_LIMIT` 400、`DAILY_TOTAL_LIMIT` 1,000。確認の通しが、1 人あたりの上限 60 に当たらないようにするため）。引き上げた上限は、設定を付けない通常のデプロイで、標準の値（60 と 400）に戻した。標準の設定は 60 と 400 である（戻したことの根拠は [docs/dev-log.md](../docs/dev-log.md) の 6.1。デプロイされている変数は、公開前に確かめる）。書式の規則を足した再デプロイ（バージョン e525d8b9-3560-493f-89b1-a9a511e022cf）も、出力の設定の一覧に `DAILY_*` の変数は無く、標準の 60 と 400 のままである。

1. **Anthropic のコンソール**で、この Worker 専用のワークスペースを作る。**キーを作る前に**、そのワークスペースに次の 3 つを設定する。
   - 月の利用上限（spend limit、約 100 ドル）。これが、お金を確実に止める唯一の上限です。
   - 利用額の通知（約 25 ドル）。
   - レート制限（毎分のリクエスト数と、毎分の入力トークン数。低めに）。Worker の数え上げは目安ですが、これはサーバー側で一括して効く速度の上限です。
2. **Cloudflare のプランが Workers の有料プラン（Paid）であることを確かめる。** 無料プランでは、KV の書き込みがアカウント全体で 1 日 1,000 回までで、通した 1 回の呼び出しが 2 回書くため、約 500 回で書き込みの枠が尽きます。尽きたあとは書き込みが失敗し、保存できない要求は断る（fail closed）ので、**00:00 UTC まで AI が 503 で止まります**（上限が外れるのではなく、止まります。上流は呼ばないので、お金は使いません）。同じアカウントのほかの Worker の分もこの枠に入ります。有料プランならこの枠が無く、止まりません（読み取りも無料プランは 1 日 100,000 回までで、1 回の判定が 17 回読みます）。
3. KV の名前空間を作る: `npx wrangler kv namespace create RATE_KV -c worker/wrangler.jsonc`。出た `id` を `worker/wrangler.jsonc` の `kv_namespaces[0].id` の仮の値（`REPLACE_WITH_REAL_KV_NAMESPACE_ID`）に手で置き換える。設定ファイルに追記するかと聞かれたら**いいえ**と答える（追記されると、仮の値の隣に 2 つ目の `RATE_KV` ができる）。
4. レート制限の `namespace_id`: `worker/wrangler.jsonc` の `ratelimits[0].namespace_id`（既定 `"21001"` は仮の番号）を、**6 桁のランダムな正の整数**に書き換える（例: `python3 -c 'import random; print(random.randint(100000, 999999))'`）。同じ番号のバインディングは数えを共有してしまうが、アカウント内の番号を一覧するコマンドは無く、「未使用を確かめる」ことはできないので、ランダムな 6 桁にして偶然の重なりを避ける。`limit` 20・`period` 60 はそのまま（`wranglerConfig.test.ts` が固定しています）。
5. 秘密を登録する（コードにも設定ファイルにも書かない）: `npx wrangler secret put ANTHROPIC_API_KEY -c worker/wrangler.jsonc`（手順 1 の専用ワークスペースのキー）と、`npx wrangler secret put IP_HASH_SECRET -c worker/wrangler.jsonc`（長いランダムな文字列）。まだデプロイしていない Worker に初めて秘密を入れるとき、wrangler が「その名前の Worker は無い。新しく作って秘密を足すか」と聞くので、**はい（y）**と答える（中身は手順 7 のデプロイで入る）。
6. `ALLOWED_ORIGINS` を、公開ページの出どころだけにする。Pages のプロジェクトは手順 8 で作るので、ここでは**予定のプロジェクト名から決まる出どころ** `https://<プロジェクト名>.pages.dev` を入れる。**末尾の `/` は付けない**、完全一致、`http://localhost:5173` は外す。複数ならカンマ区切り。名前が使われていて末尾に文字が付くなどして、手順 8 でできた本物の出どころがこれと違ったら、ここを直して手順 7 をもう一度行う。
7. **Worker をデプロイする**: `npx wrangler deploy -c worker/wrangler.jsonc`。この Worker は公開の住所を持たない（`workers_dev: false`）ので、出力に URL は出ない。手順 8 の Function が、サービスバインディングで呼ぶ。出力の一覧に、`env.RATE_KV` が**本物の id**で、`env.IP_LIMITER (20 requests/60s)` と、本番の `ALLOWED_ORIGINS` が載っていることを確かめる。
8. **画面を、同じ出どころの `/api/chat` から Worker を呼ぶ形で作り、公開する**: `VITE_CHAT_ENDPOINT=/api/chat npm run build`（ビルドに埋め込まれるので、変えたら作り直す。書かないと、画面は接続先を決めていないものとして、「AIに質問」の最初の説明文で使えない旨を先に言う。`docs/ai-endpoint.md`）。できたサイトを、手順 6 で予定した名前の Pages プロジェクトに、リポジトリのルートから `npx wrangler@4.103.0 pages deploy dist --project-name japan2100 --branch main` で公開する（ルートの `wrangler.jsonc` のサービスバインディング `CHAT_API` と、`functions/api/chat.ts` の Function が一緒に上がる。バインディングの `service` は、Worker の `name` と同じにする）。公開後の本物の出どころが `ALLOWED_ORIGINS` と一致していることを確かめる。
9. **実際の API で確かめる**（専用のキーで、本人の承認を得てから。モックでは確かめられない）。公開ページを開いてブラウザの開発者ツール（ネットワーク）で応答を見るか、`curl -H 'Origin: <公開ページの出どころ>' -H 'content-type: application/json' -d '{"messages":[…]}' https://<公開ページの出どころ>/api/chat` で応答の JSON を読む。確かめている間は、`npx wrangler tail -c worker/wrangler.jsonc`（または Workers Logs）も見る。`rate limit store unavailable` や `burst limiter unavailable` が出ていないか（出ていれば、その要求は 503 で断られている）。`IP_LIMITER` は 1 人あたり 60 秒に 20 回までで、さらに同じ人の呼び出しを 1 秒以内に 2 回送ると 2 回目が 503 で断られる（同じカウンターへの 1 秒以内の 2 回目の書き込みが断られるため）ので、続けて送るときは 1 秒以上、20 回を超えそうなら 60 秒まで間を空ける。この順に行う:
   - **まず 429 の経路**（確かめる人の回数がまだ 0 のうちに行う。先に他の確認をすると、その回数が 1 日の数に入っていて、`DAILY_IP_LIMIT` を 3 にしても最初の呼び出しから断られる）: `npx wrangler deploy -c worker/wrangler.jsonc --var DAILY_IP_LIMIT:3` で一時的に 3 にして、3 回は通り、4 回目で 429 になることを確かめる。画面は、その質問に確認済みの保存済みの答えがあれば保存済みの答えに切り替わり、無ければ「いまはAIに接続できません。保存済みの質問を試してください。」と、保存済みの質問のボタンが出る。質問の例は、保存済みの答えが中継を呼ばずに出るので、この確認には質問の例ではない質問を使う。**確かめたら、`--var` なしでもう一度 `npx wrangler deploy -c worker/wrangler.jsonc` する**（`--var` なしのデプロイは、設定ファイルに無い変数を消すので、`DAILY_IP_LIMIT` は既定の 60 に戻る）。戻ったことは、続けて 4 回以上呼んでも 429 にならないことで確かめる。この人の 1 日の回数は、ここまでの分が引かれて残る（60 − 3 − …）ので、以降の確認が足りなければ、別のアドレスから行うか、翌日（00:00 UTC のあと）に行う。
   - 9 つの道具の定義すべてが API に受け付けられる（400 にならない）。9 つ目の `get_age_groups` を足した分は、この確認がまだ（下の「手順 9 の結果」の 8 つは、足す前の通しの結果）。
   - 道具を 1 回呼ぶやり取り（`tool_use` → `tool_result` → 答え）が通る。
   - **10 問以上を続けて質問する会話**で、画面が古いやり取りを捨てたあとも 400 にならない。ただし `drop_block` があるので、思考ブロックの不一致は 400 にならず、「400 が出ない」だけでは `block_binding` が働いたかは分かりません。**応答の JSON の `input_transformations` を読む**: 古いやり取りを捨てる前のターンは `[]`、`thinking_dropped` や `prefix_binding_mismatch` が出るのは捨てたあとだけのはずです。捨てていないのに毎回出るなら、画面か Worker が履歴を毎回書き換えていて、思考が黙って捨てられています。
   - **`usage` と `stop_reason` を、10 問のすべての応答で読んで記録する。** 5 分以内の 2 回目の呼び出しで `usage.cache_read_input_tokens` が 0 より大きい（キャッシュが効いている）。`stop_reason` が `max_tokens` のものが 1 つでもあれば、3,000 では小さすぎる（`effort: low` でも。画面は「答えが返ってきませんでした」と出す）。`usage.output_tokens` も見る。`effort: low` でもモデルが必要なときに道具を呼ぶこと（呼ばずに自分の知識で答えることがある）。1 回の応答にかかる時間も見る（KV の読み取り 17 回の分が足されている）。
   - 回答を断る（`refusal`）質問をして、画面が正しく扱うこと。
   - **トークン数を測る**: いちばん簡単なのは、Worker 経由で一言の質問を送り、応答の `usage` の `input_tokens` ＋ `cache_creation_input_tokens` ＋ `cache_read_input_tokens` を読むこと（毎回付く道具とシステムプロンプトの大きさ ＋ 数トークン。見積もりは約 4,600）。日本語 21,000 文字の質問（本文 64KB 以内）を送って同じ合計を読み、前の合計を引いて 21,000 で割れば、1 文字あたりのトークン数になる（見積もりは 1〜1.5）。測った値で「お金の見積もり」を書き直す。無料の `POST /v1/messages/count_tokens` を使うなら、Worker にはその道が無いので、**Anthropic の API に自分のキーで直接**呼び、本文に `model`・`system`（`worker/systemPrompt.ts`）・`tools`（`src/ai/toolDefs.ts`）と、**空でない** `messages` を入れる。
   - **記録された 1 行を実際に見る**: ダッシュボードの Workers Logs で、確認中に出た行（たとえば `upstream responded …` や、わざと出した失敗の行）を 1 つ開き、**接続元の IP・API キー・ヘッダーの値が入っていない**ことを確かめる（Cloudflare が付けるメタデータの中身を確かめる唯一の方法。「ログ」の節）。入っていたら、`wrangler.jsonc` の `observability` を見直す。
10. **イベントが終わったら**: 専用のキーを失効させるか、`DAILY_TOTAL_LIMIT` を `0` にして AI を止める。

## 設定

| 名前 | 種類 | 内容 |
|---|---|---|
| `ANTHROPIC_API_KEY` | 秘密 | Anthropic の API キー。応答にもログにも出しません。 |
| `IP_HASH_SECRET` | 秘密 | IP を変換する HMAC の鍵。未設定なら 503 `server_misconfigured`。 |
| `RATE_KV` | KV | 日ごとの数え上げ。IP ごとの `ip:<日付>:<HMAC>` と、全体の `total:<日付>:<0〜15>` の 16 個（キーは UTC の日付つき、2 日で消えます）。 |
| `IP_LIMITER` | Rate Limiting | 短時間の連続の制限（60 秒に 20 回、`wrangler.jsonc` の `ratelimits`）。必須で、無いと 503 `server_misconfigured`。 |
| `ALLOWED_ORIGINS` | 変数 | 呼び出してよい出どころ（カンマ区切り）。 |
| `DAILY_IP_LIMIT` / `DAILY_TOTAL_LIMIT` | 変数（任意） | 既定は 60 / 400（上流への呼び出しの回数）。`0` で全部止められます。 |
